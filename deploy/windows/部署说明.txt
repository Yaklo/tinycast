TinyCast Windows 运行包使用说明
======================================================================

一、这个包是什么

  一个不用安装任何环境的直播服务：解压后双击就能跑。
    - MediaMTX：负责收 RTMP 流、给浏览器分发 HLS / WebRTC；
    - tinycast.exe：负责推流鉴权、房间状态、在线人数、网页。
  不需要数据库，不需要 Docker、Node.js 或 Visual Studio。
  关掉窗口后所有房间状态就没了，这是刻意保持的轻量设计。


二、目录结构

  tinycast.exe            业务后端（网页也打包在里面）
  tinycast.env            配置，改完要重启 TinyCast 生效
  start-all.cmd           一键启动 MediaMTX + TinyCast（推荐）
  start.cmd               只启动 TinyCast（MediaMTX 已单独在跑时用）
  open-firewall.cmd       放通端口，需要管理员权限
  mediamtx\mediamtx.exe   MediaMTX 主程序
  mediamtx\mediamtx.yml   MediaMTX 配置（推流鉴权回调写在这里）
  logs\                   运行日志，出问题时先看这里


三、第一次使用

  1. 把整个文件夹解压到本地磁盘（不要放在压缩包里直接运行）。
  2. 右键 open-firewall.cmd → 以管理员身份运行，放通端口（只需一次）。
  3. 双击 start-all.cmd。会弹出两个窗口：
       TinyCast - MediaMTX   媒体服务，关掉它就断流；
       TinyCast 控制台       业务后端，按 Ctrl+C 停止。
  4. 浏览器会自动打开 http://127.0.0.1:8080 。
  5. 点首页的“创建推流配置”，填用户名（3~32 位字母、数字、下划线、减号）
     和房间名称，点生成。
  6. 把生成结果里的“服务器”和“推流码”分别粘进 OBS：
       设置 → 直播 → 服务选“自定义”
       服务器：rtmp://127.0.0.1:1935/live
       推流码：整段复制，不要手改（房间名带空格或中文时尤其要注意）
  7. OBS 点“开始直播”，首页立刻出现房间；点进房间就能看画面。

  推流码形如  alex?room=%E6%B5%8B%E8%AF%95&token=MPA49Px...
  其中 alex 是用户名，room 是房间名，token 是随机令牌。
  用户名和令牌一一绑定：原连接断开后 5 分钟内可以用同样的用户名+令牌重新推流，
  但同一时刻只能有一路；换用户名必须换令牌，否则会被拒绝。


四、端口

  TCP 1935   OBS 推流（RTMP）
  TCP 8080   网页、接口，以及 /hls/ 与 /rtc/ 的反向代理
  UDP 8000   WebRTC 媒体通道（“低延迟”模式必需）
  TCP 9997   MediaMTX 管理接口，只监听 127.0.0.1，不对外

  只在本机自己看，可以不放通任何端口。
  局域网或公网观看时，TCP 1935 / TCP 8080 / UDP 8000 都要放通。


五、局域网或公网观看

  1. mediamtx\mediamtx.yml 里把 webrtcAdditionalHosts 改成这台机器的 IP 或域名：
       webrtcAdditionalHosts: [192.168.1.10]
     （只在本机测试时保持 [127.0.0.1] 即可。）
  2. tinycast.env 里把推流地址改成同一台机器的地址：
       MEDIAMTX_RTMP_PUBLIC_BASE=rtmp://192.168.1.10:1935/live
  3. 重启 start-all.cmd，用 http://192.168.1.10:8080 打开页面。

  正式对外时请在前面加一层 HTTPS 反向代理（Caddy / Nginx），
  并把 PUBLIC_BASE_URL 填成 https://你的域名 。


六、播放方式与编码

  播放器有两个通道，右上角可以切换：

    默认 HLS        有声音，支持 H.264 / H.265 / AV1，延迟 0.6～1.2 秒；
    低延迟 WebRTC   延迟约 0.3 秒，但 MediaMTX 不做转码，
                    浏览器拿不到 AAC 音轨，只有画面没有声音。

  编码建议：
    - 想要“有声音 + 各平台都能看”，用 H.264 推流，走默认 HLS 通道；
    - 想要最低延迟，必须同时满足两条：视频用 H.264，并且在 OBS 里关掉 B 帧
      （输出 → 高级 →「最大 B 帧数」改成 0；x264 自定义选项写 bframes=0）。
      带 B 帧的 H.264 会被媒体服务直接断开会话，日志原文是
      "doesn't support H264 streams with B-frames"；
    - HLS 通道不挑这些：带 B 帧、H.265 都能放，所以默认就是 HLS；
    - H.265 在 Chrome / Edge（Windows、macOS）与 Safari 上能通过 HLS 播放，
      Linux 下的 Chrome 与 Firefox 通常解不了，页面会给出提示。

  播放器右上角的 🩺 按钮是实时统计面板（面板收在播放器下方，不遮挡画面）：

    HLS 通道    视频 / 音频码率、下载速率、累计接收、帧率、直播延迟、缓冲余量；
                面板里没有 RTT / 抖动 / 丢包 —— HTTP 分片拿不到这些，不是坏了；
    低延迟通道  上面这些之外再加 RTT、抖动、丢包率。

  画面异常时先看这里：下载速率为 0 说明媒体没到，帧率为 0 说明解码没开始。

  HLS 延迟：媒体服务给的是低延迟 HLS（LL-HLS），每 0.2 秒一个分片，播放器只需停在
  直播边缘后约 0.5 秒。Chrome / Edge 一律走 hls.js（浏览器的原生 HLS 只能整段下载，
  延迟十几秒），只有 Safari / iOS 用原生播放；播放器按“离直播边缘 1.2 秒”定目标，
  落后超过 1.8 秒会自动跳到最新画面。实测 OBS 默认关键帧 4 秒时延迟 1.2 秒，
  关键帧 1 秒时 0.6 秒。🩺 面板里的“直播延迟”就是落后多少秒，控制栏也会出现
  “延迟 X s · 追平”按钮。想再低，把 OBS 的关键帧间隔改成 1 秒（分片只在关键帧处切）。

  播放方式可以在 🩺 面板里选：自动（Safari 用原生播放器，其它浏览器用 HLS.js）、HLS.js、原生。
选择会记在浏览器里，下次打开还是同一个。Chrome / Edge 没有可用的原生 HLS，所以“原生”是灰的；
Safari 上的 HLS.js 只能解 H.264，要看 H.265 就留在“自动”。
面板顶部会写明当前用的是哪个引擎，以及分发协议是 LL-HLS（分片 0.2 秒）、HLS（整段分片）
还是 WHEP（低延迟通道）。看到“HLS（整段分片）”就说明是按整段播，延迟会偏高。

  延迟档位：控制栏里有一组 [自动] [低延时] [稳定]，三档都是 LL-HLS，只是目标延迟不同：

    低延时  1.2 秒，缓冲 4 秒，落后超过 1.8 秒自动追到最新画面；
    稳定    3 秒，缓冲 6 秒，不主动追 —— 弱网、投屏、公共 Wi-Fi 用这档；
    自动    默认，先按 1.2 秒播；发现一分钟内被追平两次以上、缓冲反复见底或下载速率
            明显低于码率时，单向放宽到稳定档的参数，不会自己降回来（重选或刷新才恢复）。

  手动点档位会重建一次播放器，画面黑 0.3~1 秒；自动放宽是热改参数，不闪屏。
  面板里还有个 LL-HLS 开关：关掉就退回普通 HLS（按整段分片缓冲），延迟升到十几秒，
  但请求数少约 20 倍，弱网最稳 —— 关掉后三个档位都会变灰。

  播放中鼠标静止 2.5 秒，控制条会自动收起，动一下鼠标或点一下画面就回来。

  低延迟通道（WebRTC）连上 6 秒还没画面时，播放器会自动切回 HLS 并在画面上
  说明原因；改好 OBS 的 B 帧设置后重新推流，再点“低延迟”即可。


七、出问题怎么查

  ① 首页点了房间，画面一直转圈
     先看 logs\tinycast.log 有没有“推流鉴权通过”和“推流开始”。
     没有“推流鉴权通过”= 推流码不对（令牌不匹配、用户名已被别的令牌占用）。
     有“推流开始”但画面不动 = 浏览器与媒体之间不通，检查：
       - 用的是 WebRTC 通道？OBS 必须关掉 B 帧（最常见原因，见第六节）；
         现在播放器会自动回退到 HLS，若仍然黑屏再往下查；
       - 局域网观看时 UDP 8000 是否放通；
       - mediamtx.yml 的 webrtcAdditionalHosts 是否写成了这台机器的 IP；
       - 是不是 H.265 却在 Linux 浏览器上用 HLS 通道播放。

  ② OBS 提示连接失败或被拒绝
     - 推流码是否整段复制（形如 username?room=...&token=...）；
     - 同一用户名+令牌是否已在别处推流（日志里会写“已有相同身份推流”）；
     - 换过用户名却复用了旧令牌，也会被拒绝（用户名与令牌一一绑定）。

  ③ 端口被占用（窗口一闪而过 / 日志里 bind 失败）
     - 1935 被别的流媒体软件占用：关掉它，或改 mediamtx.yml 的 rtmpAddress，
       并同步改 tinycast.env 的 MEDIAMTX_RTMP_PUBLIC_BASE；
     - 8080 被占用：改 tinycast.env 的 HTTP_ADDR，同时改 mediamtx.yml 里
       authHTTPAddress 的端口。

  ④ 想确认 MediaMTX 收到了流
     浏览器打开 http://127.0.0.1:9997/v3/paths/list （只在本机可用），
     能看到 live/用户名 且 ready 为 true，说明媒体侧没问题。

  ⑤ HLS 一直延迟好几秒
     - 先点控制栏的“延迟 X s · 追平”看是否只是播放端落后；
     - 长期偏高就把 OBS 关键帧间隔改成 1 秒；
     - 上传带宽打满时也会累积延迟，🩺 面板里的下载速率接近上行上限就是这种情况。
    - 面板显示“原生播放器”且延迟偏高：在 🩺 面板把播放方式改成“HLS.js”（Safari 的原生
      HLS 不读 LL-HLS 分片）；看 H.265 时不要改，Safari 的 MSE 只解 H.264。

  ⑥ 想看更详细的日志
     把 tinycast.env 的 LOG_LEVEL 改成 debug；
     MediaMTX 的日志在 logs\mediamtx.log，或直接看它的窗口。


八、安全提醒

  - 回调接口 /internal/mtx/auth 默认只接受本机与内网来源；
    如果 tinycast 前面有反向代理，请把 MEDIAMTX_AUTH_ALLOWED_CIDRS 收窄到
    代理与 MediaMTX 的地址。
    想再加一层：tinycast.env 设 MEDIAMTX_AUTH_SECRET=一串随机值，并把
    mediamtx\mediamtx.yml 的 authHTTPAddress 改成
    http://127.0.0.1:8080/internal/mtx/auth?secret=同一个值 。
  - 推流令牌只在浏览器里生成，服务端只存 SHA-256 哈希，不会出现在房间列表里。
  - 包内的 mediamtx.exe 来自 MediaMTX v1.21.3 官方发行版。
